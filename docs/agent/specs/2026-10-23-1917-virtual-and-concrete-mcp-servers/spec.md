# Concrete MCP servers: rename and tool override

Ticket: [#9](https://github.com/Refactor-Circus/Cortex/issues/9). Decisions: `decisions.md` (D-001 to D-051).

The ticket, folder and `shape.md` heading say "virtual and concrete MCP servers" because they cover both specs; this spec closes only the concrete half. The follow-up spec for virtual servers does not exist yet; it will be linked here by path once it does.

This is the first of two specs (D-013). It ships the `McpServer` → `ConcreteServer` rename and a tool-list override for class-based servers. Virtual servers (database-defined servers served over MCP) move to a follow-up spec; see "Follow-up spec". The decisions and standards that only virtual servers use (D-002, D-007, D-008, D-010, D-014, D-015) are marked as follow-up material in `decisions.md`, `shape.md` and `standards.md`.

Criteria are numbered in reading order. The numbers changed in the Round 1 revision; `spec-review.md`, "Round 1", holds the old-to-new map.

## Goal

Rename the existing `McpServer` domain to `ConcreteServer` without breaking host servers, models, policy config or stored data (through the shims of AC 3 to 7), and let Cortex override the tool list of a concrete (class-based) server the way it already overrides its instructions. The one documented break is the unshimmed classes: events, actions, Data, requests and exceptions in the old namespace move without aliases (D-043; Risks). Each AC appears in exactly one bullet (sub-criteria follow their parent):

- Rename: the folder and namespace move, unchanged public names, the regression baseline (AC 1, 2);
- Compatibility shims: morph aliases and written morph string, Gate resolution, class-name shims and old policy config keys (AC 3 to 7);
- Tool override storage and writes: the migration and missing-column fallback, the update action with its validation, race, lock, ability and guest exposure (AC 8, 9), and the guest boot warning (AC 9a, hardening);
- Serving the overridden list: ordering, flat list, host-added tools, ambiguity, per-request memo, tool-level visibility (AC 10, 10a to 10f);
- Delete and clear semantics: `DELETE …/instructions` keeps a tool override, and the clear action restores code tools (AC 11, 13);
- The `cortex` server stays non-overridable (AC 12);
- Reachability and payload: HTTP and MCP routes and tools with parity, the resource fields, and the four named consumers of tool-only rows (AC 14, 15);
- Stale, failing and corrupt entries, with the cache-based warning rate limit (AC 16, 18; the rebuild-failure fallback is in Design);
- Caching and invalidation after commit (AC 17);
- Atrium editor (AC 19);
- Renamed-table coverage, docs and the quality gate (AC 20 to 22);
- CI (D-041): `refactor-circus/keen` in `require-dev`, a `composer dump-autoload` workflow step before the tests, and a guard that the Keen-conditional tests are not skipped in CI (AC 3, 6, 22).

Must have versus hardening. Must have, they carry the goal: AC 1 to 7 (without them hosts break on upgrade), AC 8 (column and its migration), AC 9 (update action, validation, ability, guest-exposure docs), AC 10 and 10a to 10d, AC 11 to 15, AC 17, AC 19 and AC 20 to 22. Hardening, defensive extras around the same feature: the per-request memo (D-026, AC 10d, 10f), tool-level visibility (AC 10e), the cache rate limit (D-035, AC 16 and 18), the missing-column fallback (D-034, AC 8), the rebuild-failure fallback (D-028, Design), the guest boot warning (D-030, D-037, AC 9a), the rebuild-failure fallback's cache rate limit (D-047, Design, AC 16), the update action's `lockForUpdate()` re-read (D-049, AC 9), the unshimmed-name warning (D-048, AC 6), the subprocess autoload test (AC 6) and the race tests (AC 9, 11, 13). Each hardening item has its own decision (D-026 memo, D-028 rebuild fallback, D-030 guest boot warning, D-034 missing-column fallback, D-035 cache rate limit, D-041 CI), and every AC listed here is in scope while this spec stands. Every hardening layer stays in this spec (D-050); the split is a build-order hint and shows which criteria are which. Anything not under an AC or a Design heading is out of scope.

## Acceptance criteria

### Rename (D-003, D-004, D-011, D-017)

1. `src/Domains/McpServer` is gone (the shims of AC 6 and 7 live under `ConcreteServer`); its classes live in `src/Domains/ConcreteServer` under `RefactorCircus\Cortex\Domains\ConcreteServer\…`, registered by `ConcreteServerServiceProvider` from `Domains\DomainServiceProvider`.
2. Table keys (`mcp_instructions`, `mcp_instruction_versions`), HTTP route URIs and names (`cortex.servers.*`), Cortex MCP tool names, config keys (`cortex.mcp.servers`) and registered server names are unchanged: the existing HTTP, MCP and Atrium tests for servers pass. The regression baseline is the existing server test files, moved to the new namespaces: they keep every assertion unchanged apart from namespace imports (only the shim, morph-alias and old-row tests use the old strings). Machine check (D-040): an architecture test scans `tests/` and `src/` and fails when the string `Domains\McpServer` appears anywhere except an allowlist of the shim, morph-alias, old-row, old-policy-key and subprocess fixture files (the shim file itself is one of them); the allowlist is a fixed set of named files that the test asserts exactly (members and count), so it cannot grow silently, and so a moved test cannot keep an old import or the old namespace in src.
3. Morph resolution. `keepMorphAliases()` in `ConcreteServerServiceProvider` registers exactly these morph map entries (key = old FQCN, value = new class):
   - `RefactorCircus\Cortex\Domains\McpServer\Models\McpInstructionModel` => `RefactorCircus\Cortex\Domains\ConcreteServer\Models\McpInstructionModel`
   - `RefactorCircus\Cortex\Domains\McpServer\Models\McpInstructionVersionModel` => `RefactorCircus\Cortex\Domains\ConcreteServer\Models\McpInstructionVersionModel`

   Because the key is the old FQCN, `getMorphClass()` on a new model returns the old string and `Relation::getMorphedModel(old)` returns the new class. One test asserts both directions for both models, and loads a stored polymorphic row holding the old class string and gets the new model back. A second test, run only when `refactor-circus/keen` is installed (skipped otherwise, `->skip(! class_exists(...))`), loads a stored audit entry holding the old string and gets the new model back. The aliases are registered through the merging form `Relation::morphMap($map)` (never `$merge = false`, never `enforceMorphMap()`). A test registers a further host entry with `Relation::morphMap(['other' => SomeModel::class])` after boot and asserts both Cortex keys still resolve. The README states that a host calling `Relation::enforceMorphMap()` or `morphMap([...], false)` must keep these two keys, or stored rows stop resolving; this is documentation only, no test covers `enforceMorphMap()`. The README also says a host must not re-map the two model classes under another alias (a later `morphMap()` alias for the new class would win for writes and mix two strings in stored rows); the boot check below also warns when `getMorphClass()` of either new model differs from the old string, tested. Runtime signal: after all providers boot (a `booted` callback), Cortex checks that `Relation::getMorphedModel()` still resolves both old keys to the new classes; when it does not, it logs one non-fatal warning naming the key (once per process) and never throws. A test unsets the map entry, runs the check and asserts the warning; another asserts no warning when the keys resolve.
   - CI (D-041, D-040): the Keen-conditional tests here, in AC 4 and in AC 11 must run somewhere. `refactor-circus/keen` is added to `require-dev`. Machine check: a guard test that, when the `CI` environment variable is set, fails unless `class_exists()` holds for the Keen audit model, so the Keen tests cannot be skipped silently in CI (locally they still skip when Keen is absent).
4. Written morph string: new rows keep writing the old string (AC 3), so stored data stays uniform. A test asserts this for a polymorphic row written from a new save and, with Keen installed only, that an audit row written for a new save carries the old string and resolves back to the new model.
5. Gate: a policy registered for the new model class guards a record loaded from a stored old morph string. The test loads a polymorphic row holding the old string through the relation (the `Relation::getMorphedModel()` path), then asserts `Gate::getPolicyFor()` returns the new policy and an `authorize` call is refused by a denying policy registered for the new class. The test does not rely on an instance created through a `class_alias` name, since that is the new class itself.
6. Class-name shims. The old FQCNs `RefactorCircus\Cortex\Domains\McpServer\Support\Server` and `RefactorCircus\Cortex\Domains\McpServer\Concerns\HasVersionedInstructions` remain as aliases to the new classes. PSR-4 cannot autoload the old names once the folder is gone, and a service provider is too late (host classes extend them before it boots). Per D-027 the aliases are lazy: one file in `composer.json` `autoload.files` registers an `spl_autoload_register` fallback for the old `Domains\McpServer\` prefix that calls `class_alias` only when an old name is requested, so no aliased class (or its `laravel/mcp`/Eloquent parents) loads in a process that never names one. The shims are marked `@deprecated` (removed in the next major) in their docblocks and the CHANGELOG. Tests:
   - a host server extending the old `Support\Server` and one using the old trait still work (instructions override applies, and with a tool override saved the served tools change), and `class_exists()` on each old name is true and resolves to the new class (`ReflectionClass::getName()`);
   - a subprocess test: a child process started with `PHP_BINARY` runs a script that requires `vendor/autoload.php` of the package under test (resolved from the package root, never from `PATH`), declares a class extending each old FQCN and prints a marker. The child script is a checked-in fixture (`tests/Fixtures/old-namespace-child.php`), not generated at runtime. The child never boots Laravel, so no provider is booted. The test asserts exit code 0 and the marker on stdout. Precondition, asserted first with a message telling the developer to run `composer dump-autoload`: the generated `vendor/composer/autoload_files.php` lists the shim file, so the test fails for a stale autoloader instead of passing or failing for environment reasons. The failure is intended for a developer too: after `composer update` or `composer local:install` (symlinked siblings) the message says to run `composer dump-autoload` and rerun; it signals a stale environment, not a regression. Per D-038 the CI workflow runs `composer dump-autoload` after install and before the tests, so the precondition holds in CI, and the `composer test` script runs `composer dump-autoload` first, so the suite is deterministic locally too;
   - D-048, unshimmed names: requesting an old `Domains\McpServer` name that is not shimmed (an event, action, Data or exception) logs the `<old> moved to <new>` warning, defines no alias, and `class_exists()` stays false. Robustness rules for the fallback: it never throws (a recursive request or a `class_alias` on an already-loaded name is guarded, and `class_exists($new, true)` is called at most once per name). Where it logs when no app is booted is the open question on that; whichever is chosen, it must not fail. A test requests an unshimmed old name with no booted app (in the child-process fixture of the subprocess test) and asserts no exception;
   - an assertion reads `composer.json`, finds the shim file in `autoload.files`, and finds the `@deprecated` docblocks in it; the subprocess test above also asserts, before declaring its classes, that `class_exists($old, false)` is false for each old name (lazy: nothing aliased until requested). The CHANGELOG upgrade note tells hosts to run `composer dump-autoload -o` (asserted in AC 21). Limitation (also in Risks): a host with a classmap-authoritative or pre-built `vendor/` that was not regenerated after the update gets "class not found" for old names; no test covers that case.
7. Old policy keys (D-017). The two moved models (`McpInstructionModel`, `McpInstructionVersionModel`) and their two policies get shims at their old `Domains\McpServer\…` FQCNs, by the same mechanism and deprecation as AC 6. `ConcreteServerServiceProvider` remaps `cortex.policies` entries keyed by an old model FQCN to the new model class before `registerPolicies()` runs, keeping the host's policy class (old policy FQCNs as values resolve through the aliases). Each remapped key logs one deprecation warning naming the old and new keys. When a host lists both the old and the new key, the new key wins and the old one is still warned about. Tests: a host config keyed by an old model FQCN with a denying policy refuses the guarded action over HTTP and MCP (it does not fall back to the bundled allow-all policy), the deprecation warning is logged, and an old policy FQCN as the value resolves.

### Concrete server tool override (D-005, D-009, D-012, D-016, D-021, D-022)

8. A new migration adds a nullable json `tools` column to the `mcp_instructions` table (resolved through `Tables`); `McpInstructionModel` casts it to an array and lists it in `$fillable`. Cortex only publishes its migrations (no `loadMigrationsFrom`), so a host that upgrades without publishing and running the new migration has no `tools` column. The CHANGELOG upgrade note says to publish the migrations tag (`vendor:publish`) and run `migrate` (asserted in AC 21). Per D-034 the serving path degrades in that state: a missing `tools` column is treated as no tool override (code tools served, instructions override still applied) and one warning is logged (context key `server`, message naming the migration), rate-limited as in AC 16 (D-035). The check resolves its connection from the model (`McpInstructionModel::getConnection()`), never the default connection, so a host with a tenant or non-default connection checks the right database; a test uses a model on a non-default connection. What a throwing check does is the open question on that; the memo only ever stores a completed check result. A test drops the column (or runs without the migration) and asserts `tools/list` holds the code tools, `tools/call` works and the warning is logged. Per D-042 the migration is idempotent: it guards with `Schema::hasColumn()` (table resolved through `Support\Tables`), so running it twice is a no-op, tested; its `down()` also guards with `hasColumn()`, and rolling back drops the column and any stored tool overrides (stated in the README). The memoized missing-column check lives for the process, so a host that migrates while an Octane or queue worker runs keeps serving code tools until the worker restarts; the CHANGELOG upgrade note says to restart workers after migrating.
9. `UpdateConcreteServerToolsAction` (input `UpdateConcreteServerToolsData`, `rules(string $server)`) stores the list on the server's override row, creating it when missing; `tools` is `present|nullable|array`, each entry distinct and one of the server's code-declared tool names or a registered Cortex tool name; unknown entries fail with a 422 on `tools.N`. Per D-049 the action re-reads the server's row with `lockForUpdate()` inside its transaction and decides create-or-update from that state (as AC 11 and 13). An entry names a tool the same way everywhere: a code-declared tool's `name()` first, otherwise a `ToolRegistry` registration name (a code tool wins when both match). Validation does not reject an entry matching both (D-021); there is no qualified-name syntax. Two entries resolving to the same served `name()` fail with a 422 on the later one, so `tools/list` never holds duplicates. An empty list is valid: it is stored and served as no tools (distinct from null), tested. An unknown server answers 404 over HTTP and `Not found.` over MCP (`ServerMcpRequest`), tested.
   - Race: creating the row when missing must not 500 when two first saves collide on the `server` unique index. The test makes a `creating` listener on `McpInstructionModel` insert a competing row for the same server once, then asserts only the observable result: the action succeeds, one row exists for the server, and it holds the saved list. Where the retry runs (savepoint, outside the transaction, or `firstOrCreate`) is an implementation choice not asserted; the criterion does not depend on a driver-specific SQLSTATE. Per D-023 the test uses `DatabaseMigrations` (no wrapping transaction) on a file-based SQLite database. It runs on SQLite only (D-031); CI adds no other driver.
   - Ability: the action checks a dedicated `updateTools` ability (not the instruction `update` ability) on the server; the bundled policy allows it, like every other Cortex ability (D-009). The HTTP and MCP paths each have a policy test.
   - Guest exposure: `updateTools` can add any registered Cortex tool (including `Laravel\Ai` tools) to a server, widening what MCP clients can reach, so the README, the `config/cortex.php` policies comment and the policy's docblock state that the bundled default allows guests and give a deny-by-default policy snippet (`updateTools` returns false unless the user is authorized). Registry membership is the opt-in: a registered tool is selectable on any overridable server, and a tool is otherwise selectable only if the server's code declares it. A policy test registers a denying host policy and shows it blocks a tool addition over HTTP (403/401), MCP and the Atrium screen, with the stored list unchanged. Privilege note: `updateTools` is checked on the server only, so any role granted it can expose any registered tool (including host-registered `Laravel\Ai` tools that the host restricts elsewhere) to every MCP client of that server, whatever the server's transport auth. The README warning states this next to the guest warning. Per D-033 this is the trust boundary: no per-tool ability is checked, and the README and the policy docblock document `updateTools` as the trust boundary (a per-tool ability is a follow-up).
   - Host policy without `updateTools`: a host policy registered for `McpInstructionModel` that does not define `updateTools` goes to the Gate's default, which denies, so the update and clear routes and tools and the Atrium tool editor refuse (403 for a signed-in user, 401 for a guest). The bundled guest-allowing default stays as decided (D-009, D-046). Tested once (a host policy class without `updateTools` refuses the update over HTTP and MCP and the stored list is unchanged); the CHANGELOG upgrade note and the README say so.

9a. Guest boot warning (hardening; D-030, D-037, D-039). Upgrade surfacing: the bundled default stays, and outside the `local` environment Cortex logs a warning when the resolved policy allows `updateTools` to a guest (checked with `Gate::forUser(null)`, not per request), naming `updateTools` and pointing to the README snippet. Robustness rules that hold either way: the check never throws (a policy that throws, hits the database or a missing table, or assumes a user is caught and logged nothing), it does not run when booting in the console (`migrate`, `package:discover`, CI before migrations), and it passes the same arguments as the action's check (the ability `updateTools` and the registered server name, evaluated for the overridable servers). Per D-037 the provider's `booted` callback calls a public method that runs the check, guarded by a once-per-process static flag; a static reset method clears the flag, and every boot-warning test resets it in `beforeEach`; tests call the check method directly to vary the conditions within one process, and a further test asserts a second call in the same process logs nothing. The check stays cheap: it reads the policy and config directly, does no I/O of its own, and skips evaluating the Gate when the resolved policy is the bundled default. Detection rule: the resolved `cortex.policies` entry for `McpInstructionModel` is compared with the bundled policy class; when it is the bundled class the check counts every overridable server as allowed for guests, otherwise it evaluates the Gate per overridable server. It repeats once per worker process (multi-worker, Octane cold start); the README says so. Mixed per-server results (D-039): the check logs once if any overridable server is allowed for guests, naming exactly those servers. Warning contract: `Log::warning` with a message containing `updateTools` and a pointer to the README snippet, and context key `servers` (the list of overridable server names for which guests are allowed). Tests: a fresh app boot in a non-local web environment logs once through the `booted` callback; the warning is logged in a non-local web environment with the bundled policy (context `servers` holds all overridable servers), not in `local`, not in the console, not when a denying host policy is registered, and a throwing policy neither fails boot nor logs the warning. Partial-allow test: a host policy that allows `updateTools` for server A and denies it for B logs once with context `servers` = `[A]`.
10. Serving. While a server's override holds a non-null `tools` list, a client connected to that server lists exactly those tools (code tools by name, registered Cortex tools built from the `ToolRegistry`); with a null list, a row whose `tools` is null, or no row, it lists the code-declared tools. A tool removed by the override is not just hidden: `tools/call` for it fails as an unknown tool, tested by asserting the test client's error response (the unknown-tool error message names the tool). Tests use the Laravel MCP test client against the overridden concrete server and assert the `tools/list` names and a `tools/call` result. The override row is read whether or not any instructions version is published (a tool-only row has `published_version_id` null), tested. Named sub-criteria, each its own test:
    - 10a. Order: the stored list's order is kept, and this is a product promise (D-036): Cortex builds the server context and reports the resource `tools` field in stored order. Per D-051 the order is asserted in three places: the resource `tools` field (AC 15), the tools the server context was built with, and the exact ordered names in the `tools/list` a client receives. The last holds only after a vendor pin test confirms that laravel/mcp's `tools/list` preserves the order of the context's tools (the pin fails on a laravel/mcp change that reorders, so the assertion never rests on an unverified assumption). Per D-025 the context is read through a reflection helper shared with the vendor pin test (Design, `ServerContext` pin), so a laravel/mcp change breaks both in one place. The README states the promise.
    - 10b. Flat list: a server whose code tools use `ToolSearch` grouping is served as a flat list when overridden (the grouping is dropped).
    - 10c. Host-added tools: tools a host adds in its constructor or `boot()` are part of the code tools and can be selected by the override.
    - 10d. Ambiguity: when a stored entry matches both a code-declared tool and a registered Cortex tool, the code tool is chosen (D-021), one warning is logged per ambiguous entry per context build (context keys `server` and `entry`), and the resource lists the entry in `ambiguous_tools` (AC 15). A test registers a Cortex tool under the same name as a code tool after the override was saved: the served tool stays the code tool, the warning is logged and `ambiguous_tools` names the entry. Per D-026 the server context is built once per request (memoized), so one client request logs exactly one warning per ambiguous entry; a test makes one client call and asserts exactly one warning per entry, and another builds the context twice within one request and asserts the warnings are not repeated. The resource computation (AC 15) does not log.
    - 10e. Tool visibility: a selected tool keeps its own gating. A code or registered tool whose `shouldRegister()` / eligibility is false stays hidden from `tools/list` and `tools/call` after being selected by the override, and a `Laravel\Ai` tool wrapped by `AiToolAsMcpTool` keeps its own gating. Tested with a fixture tool whose `shouldRegister()` returns false, and with a `Laravel\Ai` tool wrapped by `AiToolAsMcpTool` whose own eligibility is false (hidden) and then true (served), asserting the MCP request context (guest or signed-in user) reaches the tool's own authorization. Cortex's own management tools (`update-server-tools` and similar) are not offered to agents and are not in the `ToolRegistry`, so they are not selectable unless a host registers them; the README states that registering them is the host's responsibility.
    - 10f. Memo scope: the memo of AC 10d is request-scoped (preferably a request-scoped container binding, not a static or a property of a reused server instance). A test updates the override between two requests in the same process (same container, as under Octane or repeated test-client calls) and asserts the second request serves the new list.
11. Delete semantics (D-018). `DeleteMcpInstructionAction` (`DELETE servers/{server}/instructions`, `delete-server-instructions`) clears instructions only: inside its one transaction it deletes the row's versions, nulls `published_version_id`, and removes the row only when its `tools` is null, decided from a locked read (inside the transaction it re-reads the row with `lockForUpdate()` and decides from that state, never from a read made before the transaction, so a concurrent tools save is not lost; it no longer calls `$instruction->delete()` unconditionally, which would cascade the versions through the `2026_01_01_000004` FK and drop `tools`). A row that keeps a non-null `tools` stays, its tool override still applies, and it resolves instructions from code and shows normally. The delete action forgets both cache keys after commit, whether or not it removed the row. Per D-029 the versions are deleted through models, one at a time, so each fires its `{Entity}Deleted` model events and, with Keen installed, writes its audit entry; a test asserts the events per version (and the audit entries when Keen is installed). This changes `DELETE` for existing callers, who previously got the whole override removed; the CHANGELOG and the README migration notes state it as a behaviour note (AC 21). Tests assert the database row (versions, `published_version_id`, `tools`) and the served tool list and instructions afterwards. One test starts from an override created by a prior flow (instructions plus tools); after `DELETE` the response is the updated server resource showing `tools_overridden` true and the tools are still served, so a caller can see that the tool override survived. Race test: a `tools` write that commits after the action starts but before its removal check keeps the row and its tools; the row is not deleted and no version is cascaded away. Simulation mechanism (one, fixed): a listener on the delete action's starting event writes `tools` on the row with a plain query-builder update (the starting event fires before the transaction, so the write lands before the locked re-read); the test asserts the listener ran (a flag), so it cannot pass vacuously. Rollback (events and audit): model events fire inside the transaction, so when the transaction later fails, `{Entity}Deleted` events and Keen audit writes for versions already deleted in it have been dispatched though the rows come back. Keen audit rows live in the same database connection and roll back with the transaction; model events are accepted as at-least-once (listeners must tolerate a delete that was rolled back; stated in the README and Risks). A rollback test beside AC 17(c) makes the delete action fail inside its transaction (a model listener that throws on the second version delete) and asserts every version and the row remain, `published_version_id` is unchanged and no cache `forget` ran.
12. The `cortex` server is the only non-overridable server, as a rule in `McpServerRegistry` keyed by registered name (`supportsToolOverrides()` is false for the name `cortex` only; a host subclass of `CortexServer` registered under another name is overridable, which is stated here and tested once). The update action refuses it with a 422, tested. A row with `tools` inserted directly for `cortex` is ignored when serving: the test connects to `CortexServer` through its registered route with the Laravel MCP test client and asserts `tools/list` holds the code tools. Per D-032 the `cortex` server's Atrium screen (and any non-overridable server's) hides the tool editor and the "restore code tools" button; an Atrium test asserts neither the `tools[]` checkboxes nor the `restore` button render for `cortex`. The resource for `cortex` reports `tools_overridden` false.
13. Clear the tool override, restoring code tools (D-019). `ClearConcreteServerToolsAction` with input `ClearConcreteServerToolsData` (`rules(string $server)`), starting and finished events `ConcreteServerTools{Clearing,Cleared}ActionEvent`, one transaction, and the same dedicated `updateTools` ability as AC 9 (no separate ability). It sets `tools` to null and never touches instructions, versions or `published_version_id`; the row is then removed only when it also holds no versions and no published pointer, decided from a `lockForUpdate()` re-read inside the transaction (as AC 11), so a version created or published concurrently keeps the row; a test mirrors the race test of AC 11, with the same mechanism: a listener on the clear action's starting event creates a version for the server through the model, asserts the listener ran, and the row is kept. So a clear on a tool-only row removes the row and a clear on a row with instructions keeps it. It forgets `mcpToolsKey()` (and the instruction key when the row is removed) after commit. It refuses the `cortex` server with a 422, answers 404 over HTTP and `Not found.` over MCP for an unknown server, and clearing a server with no override is a no-op that succeeds. Tests assert the database state (`tools` null, instructions and versions untouched, row kept or removed as stated) and the served tool list (code tools) afterwards.
14. Reachability. The two tool actions are reachable over HTTP and MCP, both wrapping the action: update at `PUT cortex/servers/{server}/tools` (route `cortex.servers.tools.update`) and MCP `update-server-tools`; clear at `DELETE cortex/servers/{server}/tools` (route `cortex.servers.tools.destroy`) and MCP `clear-server-tools`. Each has an HTTP/MCP parity test (same stored state and equivalent payload for the same input, and Keystone's `Testing\Parity::gaps()` lists no unreachable action). Per the test-layers standard, the validation and name-resolution rules of AC 9 are tested once at the action; the HTTP and MCP tests only check the 422/404 mapping, the route by name, authorization and the resource payload.
15. Resource payload. The concrete server resource (`McpServerResource` and the instructions show payload) reports `tools` (the effective list), `tools_overridden` (bool), `missing_tools` (stored entries that did not resolve or whose tool threw while being built, AC 16; an empty list when none and when the override is null) and `ambiguous_tools` (stored entries that matched both a code tool and a registered Cortex tool; empty when none). `schema()` declares all four. Tests: the payload for no override, an override with valid entries, an override with a stale or ambiguous entry, and an override with an entry whose tool throws while built (reported in `missing_tools`), over HTTP and MCP (parity, AC 14). A server with no row reports `tools_overridden` false and its code tools on list and show (the same applies to the `cortex` server). Tool-only rows (AC 11 and 13 create them: `tools` set, `published_version_id` null, no versions) are covered by tests for exactly four consumers: the server list resource and the instructions show payload report the instructions-overridden flag false and `tools_overridden` true, the version list is empty, publishing a version still works on it, and the Atrium server screen renders it with code-derived instructions. No other consumer is covered by this criterion; history, the Atrium list and delete-by-id flows against a tool-only row are an accepted untested gap (Risks).16. Stale and failing entries (D-016, D-022). When a stored `tools` entry no longer resolves (a code tool removed from the server class, or a Cortex tool no longer in the `ToolRegistry`), or resolves but its tool throws while being built, serving skips it, logs a warning, and lists the rest; `tools/list` and `tools/call` never fail because of it. Log contract: one `Log::warning` per such entry per context build, with context keys `server` (the server name) and `entry` (the stored entry name, a string); for a throwing tool the context also carries the exception message. Tests: (a) an override with a valid and an unregistered name; the client lists only the valid one, the warning is asserted with `Log::spy()` / `Log::shouldReceive('warning')` against exactly that contract, and the resource reports the unregistered name in `missing_tools`; (b) a registered fixture tool whose construction throws: the client lists the other tools, `tools/call` for the rest works, the warning carries `server`, `entry` and the exception message, and the resource reports the entry in `missing_tools`. Warning counts follow the rule of AC 10d (context memoized per request, exactly one warning per entry per client request, D-026). Order of the two limiters: the per-request memo applies first (one build per request), then the cache limiter decides whether that build's warning is written; the per-request count assertions of AC 10d clear the cache store between requests, so the cross-request limiter does not suppress them. Per D-044 the TTL is a new key under `cortex` in `config/cortex.php`, documented in its own banner section, read with an int cast and a hard default on every read (`architecture/configuration`). The key is `cortex.mcp.warning_ttl`, default 3600 seconds (D-045); the tests below set the key through the config repository and time-travel past the configured value, never past a hard-coded number. Cache robustness (whatever the TTL): the limiter's cache calls are wrapped so a throwing store (Redis down, serialization error, read-only file store) falls back to logging the warning and never fails `tools/list` or `tools/call`; the claim uses an atomic `Cache::add` instead of check-then-store; the key is built from the server name and a hash of the entry (or `value_type` / column name), so its length is bounded; the missing-column check of AC 8 is memoized per process (never a query per MCP request, and no caught query error inside a transaction). Limiter keys carry the Cortex key family prefix used by `PublicationCache`, so a cache shared between apps or tenants does not suppress another app's warnings, and the TTL read is clamped to at least 1 second. Per D-047 the rebuild-failure warning of Design goes through the same limiter, keyed by server name plus exception class: two requests within the TTL log once and two exception classes log independently, tested. Rule for every warning-count and limiter test (AC 8, 10d, 16, 18): `beforeEach` flushes the cache store, so no earlier test's key suppresses a warning. The throwing store is a real `Store` registered as a cache driver in the test (not a facade mock), and the test asserts it was called. A test uses that store and asserts serving still works and the warning is logged. Across requests (D-035), the stale, failing, ambiguous, corrupt-value (AC 18) and missing-column (AC 8) warnings are rate-limited through the cache: each logs only when no cache key for its server and entry (or `value_type`, or the column) exists, then stores the key with a TTL, so a persistently wrong entry logs once per TTL window. Tests: two client requests within the TTL log one warning per entry; after the key expires (time travel) the warning logs again; different entries on the same server are limited independently.
17. Caching. The published override map and tool overrides are read through `PublicationCache` and invalidated after commit by the actions that change them (update, clear, delete). The cache store must be shared across application nodes, as for the existing publication cache; the README states that a per-node store (array, file) never sees invalidations from another node. Tests use the `array` cache store and, per D-023, `DatabaseMigrations`, so `DB::afterCommit()` is genuinely exercised: (a) read, mutate through the action, read again returns fresh data; (b) the forget runs after commit: a spy replaces `PublicationCache` (or wraps `forget`) and records `DB::transactionLevel()` at each `forget` call; under `DatabaseMigrations` there is no wrapping transaction, so the test asserts every recorded level is 0 (a forget inside the action's transaction would record 1 or more) and that at least one forget was recorded, so it cannot pass vacuously; (c) rollback: warm the cache, make the action fail inside its transaction (e.g. a model `saved` listener that throws), then assert the database is unchanged, the spy saw zero `forget` calls, and a subsequent read returns the previous (old) value. Test (c) only proves deferral together with (a) and (b) under the same mode, so all three run in it. Failed forget: the after-commit `forget` is wrapped so a throwing cache store is logged and never fails the action's response or the committed write; a test makes the store throw on `forget` and asserts the action still succeeds and the failure is logged. Consequence (also in Risks): the old value stays served until the key expires or the next successful forget.
18. Corrupt stored value. Reading a stored `tools` value that is not an array (e.g. a scalar written directly into the json column) treats it as null, logs one warning per context build with context keys `server` (the server name) and `value_type` (PHP's `get_debug_type()` of the stored value, for example `string`; there is no `entry` key because a scalar has no entry name), and serves the code tools; tested with `Log::spy()` against exactly those keys. Cross-request deduplication follows the cache rate limit of AC 16 (D-035).
19. Atrium. The concrete server screen gains a tool override editor: a checklist, plus a "restore code tools" button wired to the clear action of AC 13. The checklist lists, in this order, the server's code-declared tools in code order, then the registered Cortex tools in registry order; each item shows its name and is checked when in the stored list, and stored entries that no longer resolve appear as extra items marked as unresolved (using the `missing_tools` names). Saved order follows the stored order for entries already in the list and the checklist order for the rest; no reorder control exists (see Out of scope). Saving with nothing ticked stores an empty list (no tools served), so the form requires an explicit confirmation checkbox for that case and refuses to save an empty selection without it. The form hook names are fixed in Design, "Atrium form hooks". Views use only `x-atrium::*` components; `StylesTest` passes. Atrium feature tests assert: the render shows each code tool and registered tool name with the right checked state and marks a stale entry as unresolved; saving an override and restoring code tools produce the database state; an empty selection without confirmation is refused with the stored list unchanged, and with confirmation stores `[]`. Order test: with stored `['b','a']` and a checklist of `a`, `b`, `c`, ticking `a`, `b` and `c` and saving stores exactly `['b','a','c']`; ticking `b` and `c` only (unticking `a`) stores exactly `['b','c']`.

## Design

### Domain

- **ConcreteServer** (renamed `McpServer`): namespaces and folder only. Class names keep their `McpInstruction*`/`McpServer*` stems except the service provider (`ConcreteServerServiceProvider`); renaming the classes themselves is not needed for D-004 and would churn every test (see Out of scope). `Support\Server` and `Concerns\HasVersionedInstructions` move to the new namespace; the old FQCNs stay as shims (D-011, AC 6).
- `keepMorphAliases()` (as `cortex/domains` describes) is added in `ConcreteServerServiceProvider` for the two models, with the map of AC 3.

### Concrete server tools

- `McpServerRegistry::defaultTools(string $name): list<string>` reads the server class's `$tools` default by reflection (no instantiation), flattening `ToolSearch`-grouped entries, and names each tool class with its `name()`. `supportsToolOverrides()` is false for `cortex` only (D-012).
- A scoped `McpToolOverrides` service (beside `McpInstructionOverrides`, same `PublicationCache` key family, new `mcpToolsKey()`) maps server name → list. It selects every row with non-null `tools`; `McpInstructionOverrides` filters on `published_version_id` and cannot be reused for this. Every action that changes `tools` or deletes the row forgets `mcpToolsKey()` after commit (the delete action forgets both keys). A stored value that is not an array is read as null (AC 18).
- At serve time the code tools come from the parent `createContext()` result (so tools a host adds in its constructor or `boot()` are included, AC 10c), selected by `name()`; the reflection read of `$tools` in `defaultTools()` only feeds validation and the screens, and the docs say a server building its tools dynamically shows the reflected list in validation. A server whose code tools use `ToolSearch` grouping is served as a flat list when overridden (AC 10b).
- `HasVersionedInstructions::createContext()` grows into `HasCortexOverrides` (trait kept under its old name too, delegating) and, when a tool override applies, rebuilds the `ServerContext` with the overridden tools: code tools by class, registered Cortex tools from `ToolRegistry` — MCP tool classes as is, `Laravel\Ai` tools through `Support\AiToolAsMcpTool`. Unresolvable entries and entries whose tool throws while built are skipped and logged (AC 16); an entry matching both a code tool and a registered tool takes the code tool and is logged (AC 10d).
- `ServerContext` rebuilding depends on laravel/mcp's constructor and protected `$tools`; a vendor test pins it, like the existing note on `$instructions`: it reflects on `ServerContext` and fails when the constructor parameters or the `tools` property differ from what the rebuild uses, and it rebuilds a context from a real server and serves it end to end. Per D-028, when the rebuild fails at runtime (a laravel/mcp internals change, or an exception from the rebuild itself), serving logs one warning (context keys `server` and the exception message), rate-limited through the D-035 limiter keyed by server name plus exception class (D-047, AC 16), and serves the code-declared tools unchanged, with the instructions override still applied; a test forces the rebuild to throw and asserts the warning, the code tools on `tools/list` and a working `tools/call`.

### Atrium form hooks

Fixed so the tests and the views agree: the form posts `tools[]` (one checkbox per item, value = the tool name, `checked` when stored), `confirm_empty` (the explicit confirmation checkbox, value `1`), a submit button named `save` for saving and a separate form with a submit button named `restore` that posts to the clear action. An unresolved item is a checkbox with the same `tools[]` name whose visible label ends with the text `(unresolved)`; this is the one marker (it needs no `data-*` passthrough from Atrium's components, so the test is deterministic) and the test asserts that label. The render-order assertion compares the ordered list of `tools[]` checkbox values with the expected checklist order.

`ConcreteServerTools{Updating,Updated}ActionEvent` for the update action and `ConcreteServerTools{Clearing,Cleared}ActionEvent` for the clear action (AC 13).

## Out of scope

- Virtual servers (follow-up spec).
- Proxying or aggregating remote (third-party) MCP servers.
- Renaming public names (routes, tool names, config keys, tables) to "concrete server" (D-004).
- Renaming the class stems (`McpInstruction*`, `McpServer*`) to `ConcreteServer*`; only the namespaces, folder and service provider change.
- A public `#[LockedServerTools]` attribute or any way to lock other servers (D-012).
- Overriding the tools of the `cortex` server itself.
- Overriding anything on a concrete server other than its tool list (per-tool descriptions, schemas or annotations). Instructions overrides already exist and are unchanged.
- Ordering beyond the stored order: the Atrium editor is a checklist whose saved order follows the registry or checklist order (AC 19); there is no reorder control, and the HTTP and MCP update accepts an explicit order that is stored as given.
- A bulk or per-tool toggle on the HTTP API: the update replaces the whole list.
- Concurrent edits between the instruction editor and the tool editor on the same row: the last write to each column wins. The races of AC 9, 11 and 13 are the only ones handled, under one rule: a write never loses a row another write just filled.
- New audit or history events for tool changes: no `ListCortexHistoryTool` or history-route change; whatever Keen records for model saves is all there is.
- New middleware or auth configuration for the new `PUT` and `DELETE …/tools` routes: they use the same route group and middleware as the existing server routes; hosts secure them there.
- Aliases for events, actions, Data, requests and exceptions in the old `Domains\McpServer` namespace (D-043 keeps the narrow set; see Risks).
- An endpoint that lists selectable tools: none ships; the Atrium screen reads the registry directly.
- A versioned or audited tool override: the `tools` list is not versioned like instructions (no version rows, no publish step), and tool changes are not audited beyond whatever Keen already records for model saves of `McpInstructionModel` (AC 4 covers only the morph string on those rows).
- MCP resources and prompts for overridden servers (tools and instructions only).
- A migration or backfill path for removing the shims beyond the CHANGELOG note; hosts migrate their own class references before the next major. See the morph-string risk below.
- Per-server access control beyond the `updateTools` policy ability; a per-tool ability is a follow-up (D-033).
- The rename does not change `ListCortexHistoryTool` or any other Cortex tool: names, schemas and behaviour are unchanged (AC 2).
- Override rows whose server class is no longer in `cortex.mcp.servers` (orphan rows), including rows for names that were never registered: they stay in the database, are never served because no such server is registered, and no cleanup command ships.
- Screen behaviour for servers without a row beyond AC 15, and for the `cortex` server beyond hiding the tool editor (AC 12, D-032).
- Import or export of servers.

## Risks

- **Host servers on the old namespace** keep working through the shims (D-011); the shims are removed in the next major, announced in the CHANGELOG. The `autoload.files` entry needs `composer dump-autoload` in a host that has not yet re-run Composer, stated in the CHANGELOG upgrade note. The shims are lazy (D-027), so the aliased classes load only in a process that names an old FQCN. A host with a classmap-authoritative or pre-built `vendor/` that was not regenerated gets "class not found" for old names; the CHANGELOG says `composer dump-autoload -o` and no test covers it.
- **Rename without aliases for non-shimmed classes.** Only `Support\Server`, `HasVersionedInstructions`, the two models and the two policies are shimmed (AC 6, 7). The `McpInstruction*`/`McpServer*` events, actions, Data, requests and exceptions move without aliases. A host listener registered by the old event class name (`Event::listen`, a subscriber, a `$listen` map), a `catch` of an old exception, or a type-hint or binding of an old action stops matching silently, and aliasing cannot fix event listeners (the dispatcher keys on the dispatched class string). Queued jobs or listeners serialized before the upgrade that carry an old Data or event class fail to unserialize. The CHANGELOG and README say so (AC 21). D-043 keeps the narrow shim set and documents the break (drain queues, re-register listeners).
- **Publishing the migrations tag re-stamps files.** Cortex uses `publishesMigrations()`, so `vendor:publish` on a host that already published Cortex's migrations writes every migration again with a new timestamp, and `migrate` may then fail with "table already exists". D-042 settles it: the tools migration is idempotent (`Schema::hasColumn()`), and the upgrade notes of AC 8 and 21 tell such hosts to copy just that file.
- **Lock semantics are unproven off SQLite.** `lockForUpdate()` is a no-op on SQLite and the race tests run there only (D-031); the delete/clear re-reads and the update action's re-read (D-049) are protected on MySQL/Postgres by the lock but that is untested. The README says the lock is unverified on other drivers.
- **Clearing instructions costs N deletes.** `DELETE …/instructions` deletes versions one model at a time (D-029): N deletes, N model events and N Keen audit writes in one transaction, so a large history holds its locks longer and a listener that throws partway rolls back the whole clear. The CHANGELOG states the previous and the new response of this route (AC 11); the exact response is settled by D-057 (see the 2026-10-25 addendum).
- **Tool-only rows reach untested consumers.** Only the four consumers of AC 15 are covered; other endpoints against a tool-only row are an accepted gap.
- **Delete events are at-least-once.** Model events for versions deleted in a transaction that later rolls back have already fired (AC 11); listeners must tolerate it.
- **Stale cache after a failed forget.** If the cache store is down when the after-commit forget runs, the action still succeeds and the old value is served until the key expires or the next successful forget (AC 17).
- **Morph map overridden by the host.** If a host or another package replaces the morph map without Cortex's keys, stored rows stop resolving; Cortex logs one warning at boot (AC 3) and the README states the requirement.
- **Missing migration on upgrade**: Cortex only publishes migrations, so an upgraded host without the new migration has no `tools` column. The CHANGELOG says to publish and run it (AC 8, 21); until then serving degrades to code tools with a rate-limited warning (D-034).
- **Old morph strings are permanent until a data migration.** New rows keep writing the old FQCN as the morph class (AC 3, 4). Removing the shims in the next major requires a data migration rewriting the morph strings of polymorphic rows and Keen audit rows (or keeping the morph map entries). The follow-up for that major release must ship the migration; this spec ships none.
- **`ServerContext` rebuilding** depends on laravel/mcp internals; pinned by a vendor test. A runtime rebuild failure logs and serves the code tools (D-028), so a vendor change silently drops the override until fixed; the warning is the signal.
- **Published config with old class keys**: a host `config/cortex.php` keyed by the old model FQCN in `policies` would be silently ignored after the move (the Gate matches the new class), falling back to the bundled allow-all policy. Handled by the remap of AC 7 (D-017).
- **Guest-allowing policies** expose `updateTools` (D-009), and the tool set it can add widens what MCP clients reach; any role granted `updateTools` can expose any registered tool to a server's clients (AC 9, privilege note). Mitigated by documentation, the deny-by-default policy snippet and the denying-policy test of AC 9; the bundled default itself is unchanged, and a one-time boot warning surfaces it to installs outside the local environment (D-030).
- **Tool swap by name**: stored entries are bare names, so a Cortex tool registered later under a code tool's name does not replace the code tool (the code tool wins), and the ambiguity is logged and reported (AC 10d).
- **Empty override**: a `tools: []` update disables a server's whole tool set. It is valid by design (AC 9); the Atrium form guards it with a confirmation (AC 19), the API does not.
- **Stale cache across nodes**: a per-node cache store never sees another node's invalidation (AC 17); documented.

## Decision notes

- **Why DELETE keeps the tool override (D-018).** Clearing the tool override is a separate action from deleting instructions and never touches instructions or versions (AC 13). The Atrium "restore code tools" button goes through it, over HTTP and MCP with the parity rules of AC 14.
- **Shims stay in this spec (D-020).** The class shims (AC 6) and the policy-key remap (AC 7) are part of this spec.
- **Test run mode (D-023).** The race test (AC 9) and the cache tests (AC 17) use `DatabaseMigrations` on file-based SQLite; every other test keeps the suite's default.

## Addendum (2026-10-24)

- **Order observation (D-025).** One reflection helper in `tests/` reads `ServerContext`'s protected `$tools`; the vendor pin test and the order test (AC 10a) both use it.
- **Context memoized per request (D-026).** `HasCortexOverrides::createContext()` builds the overridden `ServerContext` once per request (memoized for the lifetime of the request; where the memo lives is an implementation choice, but it must not outlive the request under Octane or queues) and returns it on later calls, so stale, failing and ambiguous entries log exactly one warning each per client request (AC 10d, 16). A test calls the server once and asserts exactly one warning per entry; another calls `createContext()` twice in one request and asserts the warnings are not repeated.
- **Lazy shims (D-027).** The `autoload.files` shim registers an autoload fallback for the old prefix instead of eager `class_alias` calls (AC 6, 7).
- **Rebuild failure falls back (D-028).** A failed `ServerContext` rebuild logs and serves the code tools (Design).
- **Versions deleted per model (D-029).** `DeleteMcpInstructionAction` deletes versions one model at a time, firing model events and audit entries (AC 11).
- **Guest boot warning (D-030).** A one-time boot warning outside `local` when `updateTools` is allowed to guests (AC 9, 21).
- **SQLite only (D-031).** The race and migration tests run on SQLite only (AC 9, 22).
- **Cortex screen hides the editor (D-032).** Non-overridable servers render no tool editor and no restore button (AC 12).
- **Server-level trust boundary (D-033).** `updateTools` on the server is the only check; documented, per-tool ability is a follow-up (AC 9).
- **Missing column degrades (D-034).** No `tools` column means no tool override plus one rate-limited warning (AC 8).
- **Warnings rate-limited (D-035).** Stale, failing, ambiguous, corrupt-value and missing-column warnings log once per server+entry per TTL window through the cache, on top of the per-request memo (AC 16).
- **Order is a promise (D-036).** Stored order is asserted on the resource `tools` field and the served context, and the README states it (AC 10a).
- **Testable boot warning (D-037).** A resettable once-per-process flag and a public check method called from the `booted` callback (AC 9).
